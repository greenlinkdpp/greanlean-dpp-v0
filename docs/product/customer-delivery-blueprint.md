# Greanlean 客户交付产品蓝图

版本：草案 v1，2026-09-19  
负责人：产品负责人（创始人）  
用途：确定产品目标、首个可交付版本和功能取舍；具体法规字段以版本化规则库及官方资料为准。

## 1. 一句话定位

Greanlean 是面向将电池投放欧盟市场的企业的数字电池护照 SaaS。平台管理企业、型号、批次和单体数据，收集证据，生成可追溯的护照版本，并让客户、公众及获授权人员按权限访问。首期采用「Greanlean 协助录入和发布，客户登录查看、补充资料和跟踪进度」的服务模式。

平台目前保留通用 DPP 架构，但首个完整交付场景聚焦 e-bike / e-scooter 的 LMT 电池，以及经适用性判断的户储工业电池。护照对象是电池；整车或整套储能系统的其他合规工作不自动包含在电池护照交付中。

## 2. 交付对象与成功场景

示例客户：20 个电池 SKU，计划在欧盟销售合计 5000 件电池。客户提供企业资料、型号资料、批次/序列号清单和原始证明文件。Greanlean 完成资料校验、录入、审核、发布与二维码交付。客户使用自己的账号查看覆盖率、缺口、已发布护照和导出结果。消费者扫码访问公开信息；获授权者访问其允许的信息。

一次成功交付应能回答：

1. 5000 件中每件属于哪个客户、型号和批次，唯一标识是什么？
2. 每件护照从哪些企业、型号、批次和单体资料得到字段值？证据在哪里、由谁确认？
3. 哪些件已准备、待审核、已发布或需修正？失败原因能否定位到具体字段和行？
4. 扫码、公开网页和导出是否指向同一个已发布版本？受限信息是否只给获授权者？
5. 上级资料修改后，哪些未发布/已发布单体受影响，如何形成新版本？
6. 客户如何在不接触其他客户数据的前提下自行查看进度、提供资料和取得结果？

## 3. 用户和权限

| 用户 | 首期可做什么 | 不应拥有的权限 |
| --- | --- | --- |
| Greanlean 平台管理员/交付专员 | 开通客户、配置适用规则、导入和修正资料、审核、发布、处理异常 | 不能跳过留痕和发布校验 |
| 客户管理员 | 管理本企业查看账号、提交资料、查看项目/SKU/单体进度、下载交付物、反馈错误 | 不能查看其他企业；首期不直接批准或发布护照 |
| 客户查看者 | 按授权查看本企业资料与护照状态 | 不能修改或发布 |
| 公众扫码者 | 查看公开护照版本 | 不能读取内部证据和运行数据 |
| 专业/监管访问者 | 通过身份和授权读取允许范围 | 不能凭 URL 参数获得权限 |
| 设备/企业系统 | 通过独立凭据向指定单体或业务对象提交数据 | 不能代替人工审核或直接发布 |

首期的「客户提交资料」可从受控文件上传和问题反馈开始；复杂的供应商门户、客户自助录入与自助发布属于后续能力。

## 4. 产品对象与继承规则

```text
客户组织
  └─ 电池型号 / SKU
       └─ 生产批次（存在实际批次差异时）
            └─ 单体电池 / 序列号 / UPI
                 ├─ 护照发布版本
                 └─ 运行记录与生命周期事件
```

| 层级 | 典型信息 | 来源和变化规则 |
| --- | --- | --- |
| 组织 | 法定主体、地址、联系人、经济运营者角色 | 版本化；型号引用经核验的组织资料 |
| 型号/SKU | 电池类别、规格、化学体系、共用性能和文档 | 一次维护，多件复用 |
| 批次 | 生产地点/日期、批次检测、材料差异 | 仅记录真正随批次变化的资料 |
| 单体 | 序列号、唯一标识、制造信息、特例 | 每件唯一；允许受控覆盖并记录原因 |
| 动态记录 | BMS/EMS 指标、维修、安全及生命周期事件 | 与单体关联，只追加，保存来源和测量时间；按权限读取 |

发布候选按「组织 → 型号 → 批次 → 单体」解析有效字段值。每个值记录来源层级、来源记录版本、证据及覆盖原因；发布后冻结在不可变快照中。上级资料变更不得静默修改旧护照，应列出受影响单体，并经过新一轮校验、审核和发布。动态记录保留独立历史，不因静态护照发布而覆盖。

## 5. 最终平台的能力地图

| 能力域 | 客户实际获得的结果 | 首个可交付版本 V1 | 后续扩展 |
| --- | --- | --- | --- |
| 客户与账号 | 独立组织空间和账号 | 人工开通、邀请/重置、组织及产品授权、查看角色 | 客户自助开通、细粒度团队管理 |
| 项目与适用性 | 明确本项目适用哪些规则、还缺什么 | 项目、类别判断、资料清单、缺口/责任人 | 多市场、多法规组合 |
| 型号/批次/单体 | 20 SKU 和 5000 件可管理 | 继承、唯一标识、批量导入、查找/筛选/分页 | 更复杂的产品族与跨工厂管理 |
| 数据与证据 | 每项声明能追溯到来源 | 字段、单位、规则、文件版本、证据状态 | 供应商任务门户与自动取证 |
| 校验与工作流 | 错误可定位，发布有审批 | 预检、错误报告、准备度、候选预览、审核、批量发布、撤回/更新 | 客户自助审核链、规则编排 |
| 护照交付 | 每件可扫码、可导出、可追溯 | 稳定 URL/二维码、公开页、受限视图、JSON/PDF、历史版本 | 更多格式和渠道分发 |
| 运行与集成 | 单体可关联 BMS、ERP、EMS | 稳定 API 契约、凭据、来源映射、接入日志；按首客需要接通一个真实来源 | 标准连接器库、事件告警 |
| Registry | 可准备和记录外部注册进度 | 独立状态、测试/文件流程、回执留存；正式能力按官方接口验收 | 官方能力具备后的生产自动提交 |
| SaaS 运营 | 可持续服务多个客户 | 租户隔离、审计、备份恢复、监控、用量统计、工单/异常处理 | 计费、自助订阅、SLA 自动报表 |

V1 不以「支持所有行业」「自动完成法规合规」「所有 BMS/ERP/EMS 即插即用」「区块链证明合规」作为销售承诺。通用 DPP 模块和其他行业演示继续存在，但不分散首期端到端验收。

## 6. 首期页面原型范围

先画关键流程的低保真原型，再根据验证结果做可点击原型：

1. Greanlean：客户列表与开通 → 项目 → 型号/批次/单体列表 → 导入预检 → 资料与证据 → 缺口 → 审核/批量发布 → 异常。
2. 客户：登录 → 项目总览 → SKU/单体覆盖率 → 缺口和资料提交 → 已发布护照与下载。
3. 扫码访问者：二维码 → 公开护照 → 当前版本、来源说明和允许的下载。

每个页面原型必须标出角色、主要任务、空状态、错误状态、数据来源和可执行动作。原型评审先用一位真实客户的资料路径走通，再进入技术设计。

## 7. V1 验收门槛

- **完整流程**：以真实或经客户授权的代表性资料，完成一个客户从开通、20 SKU、5000 件单体导入，到校验、审核、批量发布、扫码、导出、版本更新的演练。数量是规模验收目标，不要求每件手动点一次发布。
- **一致性**：同一单体的网页、JSON 和 PDF 对应同一发布版本；已发布快照不可原位修改。
- **隔离与权限**：两个测试客户互相无法读取/修改资料；匿名访问不能取得受限字段或文件。
- **批量可恢复**：重复上传、局部错误、任务中断和重试有明确结果；不能悄悄漏件、重号或重复发布。
- **可运营**：客户能看懂状态和待办；Greanlean 能定位失败件、重试、备份并恢复；开通和交付步骤有操作手册。
- **真实性**：演示数据、人工补录和设备实测均有明确来源标记；正式证据由客户提供并核验；Registry 状态不得暗示未发生的成功。

具体性能阈值、可用性目标、保存期限和合同 SLA 应在首客需求与部署预算确定后量化，再纳入验收单。

## 8. 现有基础与主要缺口

仓库已有登录、组织/成员、型号/批次/单体表、单体创建与发布、公开护照、证据和动态数据接口。当前单体创建每次最多 100 件，后台层级页逐行选择审核/发布；P0 导入提交接口目前仅支持 BOM。组织到单体的完整有效值继承、批量发布、客户开通体验、5000 件操作与性能验收仍需完成。现有自动化测试证明部分代码契约，不能代替真实客户端到端验收。

参考：[当前代码审计](../architecture/current-system-audit.md)、[技术规格](../../SPEC.md)、[P0 验证报告](../generated/TEST_REPORT.md)、[已知法规不确定项](../regulatory/eu-battery-dpp/known-uncertainties.md)。

法规边界：[Regulation (EU) 2023/1542, Article 77 / Annex XIII](https://eur-lex.europa.eu/eli/reg/2023/1542/oj)、[欧盟委员会电池护照说明与数据点指南](https://single-market-economy.ec.europa.eu/single-market/digital-product-passport/batteries_en)。类别和字段适用性以最新正式资料及客户实际电池为准。

## 9. 待产品负责人确认的决策

1. V1 是否采用「Greanlean 代运营，客户查看/提交资料」的权限边界？
2. 首个付费试点优先 LMT 电池，还是户储工业电池？以真实客户和资料可得性决定。
3. 5000 件是首客验收规模，还是首年累计目标？这会影响批量任务、容量和运营设计。
4. 客户交付合同中，谁负责提供和确认原始声明、证据、唯一标识方案及 Registry 操作？
5. 首客必须接入的第一个外部系统是什么，数据字段和可用接口由谁提供？

在上述决策明确前，可以继续完成通用原型和技术预研；不要把假设写成对客户的正式承诺。
