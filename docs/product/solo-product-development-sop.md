# Greanlean 单人多角色产品开发 SOP

版本：草案 v1，2026-09-19  
适用范围：从一个客户问题到上线交付的完整开发周期。与[客户交付产品蓝图](customer-delivery-blueprint.md)配套使用。

## 1. 核心规则

一次只推进一个经过定义的客户结果。每项工作必须能够追溯：**客户问题 → 需求和验收 → 原型 → 技术方案 → 代码/数据迁移 → 测试证据 → 发布 → 反馈**。已有功能先盘点复用，缺口才进入开发。新想法先进入待办池，不直接插入当前开发。

「产品完成」指客户能独立完成其被授权的任务、Greanlean 能持续运营该能力；「代码完成」只是其中一个中间状态。法规或官方接口未定项保留待确认，不以开发完成替代合规结论。

## 2. 一个人切换的角色

| 角色 | 负责的问题 | 必须留下的结果 |
| --- | --- | --- |
| 产品负责人 | 为谁做、解决什么、先后顺序、何时算成功 | 产品目标、范围、优先级、验收标准、决策记录 |
| 客户研究/业务分析 | 客户实际怎么工作、资料从哪里来、谁负责 | 访谈记录、真实流程、样本数据、边界假设 |
| UX/原型设计 | 用户能否理解并完成任务 | 流程图、页面原型、状态与错误文案、走查记录 |
| 架构/数据设计 | 数据归属、继承、权限、接口、迁移如何成立 | 数据/接口契约、威胁与失败场景、迁移和回滚方案 |
| 开发 | 实现约定的用户行为 | 代码、迁移、配置、审计、操作说明 |
| 测试/质量 | 能否证明功能正确且未破坏旧功能 | 测试用例、结果、缺陷清单、回归证据 |
| 发布/运营 | 能否安全上线并持续服务客户 | 发布记录、备份/回滚、监控、客户开通/支持手册 |

同一个人可承担全部角色，但要按顺序切换视角。每个阶段结束时用对应角色的清单审查，不以「我自己知道」代替记录。客户验收、法规判断和正式商业责任需要相应责任人确认。

## 3. 从想法到上线的阶段门

| 阶段 | 要做的事 | 最小交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0. 收集和排序 | 记录客户问题、频率、风险与目标结果；归到当前版本或待办池 | 一张需求卡 | 指向蓝图中的用户和客户结果；优先级理由清楚 |
| 1. 需求发现 | 访谈/观察客户，拿真实样本，盘点现有代码与数据；列出未知项 | 场景说明、样本、现状/缺口表 | 能说明谁在什么情况下完成什么任务；关键假设有验证方法 |
| 2. 产品定义 | 写用户故事、范围、非目标、业务规则、成功指标和验收例子 | 一页 PRD 与验收清单 | 产品负责人确认目标和边界；不会只写「新增一个页面」 |
| 3. 原型验证 | 画主流程、关键页面、空/错/无权限状态；让客户或代理用户走任务 | 可点击原型、走查问题 | 用户能按原型完成任务；高风险歧义已修改 |
| 4. 技术设计 | 定数据权威来源、继承/版本、权限、API、迁移、故障和回滚；拆开发任务 | 技术方案、接口与数据契约、任务清单 | 能解释旧数据兼容和失败恢复；测试用例可从方案推导 |
| 5. 开发与自测 | 小批量实现，提交迁移与必要测试；用代表性样本自测 | 代码、迁移、测试、变更说明 | 验收项全部对应实现；类型、单元、集成、迁移检查通过 |
| 6. 独立验收视角 | 按客户流程走端到端，做权限负向、错误与规模测试；记录缺陷并修复 | 验收记录、缺陷处理、演示录像/截图（需要时） | 无阻断缺陷；客户代表确认业务结果或记录未签收原因 |
| 7. 预览与发布 | 在隔离环境迁移和演练；备份、发布、冒烟、监控、回滚准备 | 发布单、版本、环境和回滚记录 | 预览通过，生产发布条件和责任人明确，线上冒烟通过 |
| 8. 复盘与运营 | 观察使用、故障和支持请求；更新产品基线与待办池 | 反馈、指标、决策日志 | 新需求重新从阶段 0 排序，不在旧任务中无限追加 |

阶段门是防返工的证据检查，并不要求每项小改动写长文。简单修改可把 PRD、原型和技术方案放在同一张任务卡；涉及数据迁移、权限、批量发布或法规规则时必须留下完整记录。

## 4. 每个需求卡使用同一模板

```text
编号与标题：
用户与场景：谁在什么情况下要完成什么？
客户问题/当前证据：访谈、工单、样本或代码位置
目标结果与指标：用户完成什么；怎样测量
范围/非范围：本次做什么，后续做什么
业务规则：粒度、继承、权限、版本、异常
原型链接与页面状态：正常/空/错误/无权限
数据和接口：权威来源、字段、迁移、外部依赖
验收例子：至少正常、错误、越权/重复、更新四类
测试与发布：自动化、人工验收、回滚、监控
负责人/状态/决策记录：
```

状态统一为：`待发现 → 待定义 → 待设计 → 待开发 → 开发中 → 待验收 → 待发布 → 已上线 → 已验证`；`阻塞`单独标注原因和解除条件。不要用「做了 80%」代替可检验的状态。

## 5. 优先级与变更控制

按以下顺序选工作：

1. 阻碍首客完整交付或造成跨客户泄露/数据错误的事项。
2. 阻碍 20 SKU、5000 件批量运营的事项。
3. 客户高频任务的效率和可理解性。
4. 已有客户明确需要的一个外部系统集成。
5. 其他行业、通用化、自动化和展示优化。

每次只保留一个「本周期目标」，建议以可演示的客户任务为单位，而不是按页面或数据库表切分。周期开始后新增需求先写入待办池；只有阻断当前目标、安全问题或法规正式变化才调整范围。调整时记录新增内容、放弃内容、对发布日期和验收的影响。

## 6. 首期版本的建议开发顺序

1. **产品基线与客户样本**：确认首客责任主体、电池类别、20 SKU 和 5000 件实际数据结构、证据清单、客户可做的操作。
2. **原型与权限**：画 Greanlean 代运营、客户查看/提交、公众扫码三条完整流程；确定账号开通和客户隔离。
3. **数据继承闭环**：组织/型号/批次/单体有效值、覆盖和来源、上级变更影响、发布快照。
4. **规模化交付闭环**：单体导入预检与提交、队列/分批重试、批量审核发布、进度与错误报告、分页和搜索。
5. **客户验收闭环**：客户账号看状态、提交缺口资料、下载结果；两租户负向测试；5000 件演练。
6. **第一条真实集成**：选择首客确有接口的 BMS、ERP 或 EMS；完成字段映射、数据来源标注与接入监控。

后续再扩展自助开通、供应商门户、多连接器和其他行业。每一步都必须产生可演示、可测试的用户结果。

## 7. 每周的个人工作节奏

| 时间 | 以哪个角色工作 | 输出 |
| --- | --- | --- |
| 周初 | 产品负责人 | 选一个周期目标、最多 3 个可验收任务，冻结范围 |
| 开工前 | 客户研究 + UX + 架构 | 样本、原型、验收例子和技术设计齐全 |
| 开发中 | 开发 + 测试 | 每完成一小段就运行相关检查并记录结果 |
| 周末前 | 测试 + 运营 | 按客户流程演示；记录阻断项、发布状态和下一周期输入 |

若一项工作一周内仍不能演示，可拆为更小的端到端切片，例如「100 件导入可恢复」先于「5000 件全量发布」，而不是只完成数据库表。

## 8. 发布完成定义

一项能力只有同时满足以下条件才标为「已验证」：

- 对应的客户任务和验收例子实际走通；原型与实现一致。
- 数据来源、权限、错误和审计可解释；不同租户及匿名访问测试通过。
- 相关自动化测试、数据库迁移/回滚验证和既有公开护照回归通过。
- 预览环境使用代表性数据验收；生产备份、监控、回滚与冒烟完成。
- 用户说明和 Greanlean 操作手册已更新；遗留限制写入发布记录。
- 客户代表对其业务结果签收；尚未签收时状态保持「已上线、待验证」。

## 9. 此 SOP 的第一个工作包

工作包名称：**首客电池护照 V1 定义与原型**。此工作包先不写业务代码。

输入：一位候选客户的真实 SKU 表、单体/批次清单样本、现有证明材料目录、目前账号与操作流程。  
输出：客户场景与责任边界、V1 字段/证据清单、三条用户流程原型、20 SKU/5000 件验收方案、按优先级排序的开发待办。  
退出条件：能够让客户沿原型说明「资料如何给、谁来确认、5000 件如何生成、如何查看和更新」，并能逐条指向系统要实现的行为。

此后才进入技术方案和编码。已有 `SPEC.md`、`PLAN.md`、历史 PRD 和实施报告仍是技术与历史记录；本蓝图和 SOP 用来决定下一步做什么，避免把旧计划中的所有事项同时当作首期交付范围。
