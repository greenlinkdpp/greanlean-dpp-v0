# V1 → V2 风险登记表

## 1. 评估方法

风险等级综合考虑影响和发生可能性：

- **Critical**：可能造成跨租户泄露、错误公开、重大合规事件或不可恢复的数据损失，且当前缺少可靠控制。
- **High**：可能导致生产中断、版本错误、显著数据丢失或权限绕过。
- **Medium**：会造成局部功能失败、运维负担或互操作性下降，但可在有限范围内恢复。
- **Low**：影响有限且已有成熟缓解措施。

风险等级是当前代码与仓库证据下的审计判断；生产配置、已安装迁移和备份状态尚未获得远程证据，确认后应重新评级。

## 3. 首要风险与立即控制

在任何 V2 实施前，优先关闭以下五类风险：

1. **租户归属与隔离不完整（R-02/R-03/R-04）**：先定义 Tenant、Partner Binding 和统一授权，再迁移业务数据。
2. **公共发布不是单一不可变真源（R-12）**：禁止草稿或实时表改变已发布结果。
3. **生产状态与恢复能力未知（R-29/R-32）**：获取迁移账本、备份和恢复演练证据。
4. **旧标识、URL 与二维码兼容风险（R-14/R-15/R-16）**：统一 Resolver 并建立全量兼容测试。
5. **跨境与高权限凭据风险（R-21/R-28）**：先完成数据分类、区域策略和密钥治理。

## 4. 风险所有权

每个风险在实施前必须分配：

- 业务 owner：确认数据语义、客户影响与可接受差异；
- 技术 owner：交付控制和自动化测试；
- 安全/隐私 owner：确认授权、凭据、驻留和跨境要求；
- 运营 owner：监控、事故响应、备份与恢复；
- 最终接受者：对残余风险签字，不能由实现者自行默认接受。

## 5. Go/No-Go 阻断条件

以下任一条件成立时，不得切换生产流量：

- 存在未解释的跨租户读取、Partner 越权或 tenant 为空记录；
- 不能证明已发布 DPP 的不可变性；
- 旧二维码、URL 或关键 API 的兼容测试失败；
- 迁移存在未知字段丢失、关系断裂或未批准的自动推断；
- 备份恢复、回切、密钥轮换或事故响应未完成演练；
- Critical 风险没有有效控制或正式残余风险接受；
- 生产 Schema 与仓库迁移存在未解释漂移；
- 监控无法在用户报告前检测关键故障。

## 6. 回滚原则

- V1 在兼容窗口内保持可运行，不立即删除表、路由或对象。
- 所有切换以租户或能力为最小单位，并配套 kill switch。
- 数据迁移按 `migration_run_id` 可逆；V1 原始数据保持只读证据。
- 已发布 DPP 回滚为“切换指针到上一不可变版本”，不覆盖历史内容。
- 外部 Registry 的撤销或更正是独立业务动作，不能假设数据库回滚会自动撤回外部状态。
- 回滚后对时间窗内的新写入进行事件重放和校验，防止静默丢失。

## 7. 审计结论

V2 的主要风险不是技术栈本身，而是边界语义尚未完全统一：谁拥有数据、产品处于哪个层级、哪个 DPP 版本对外有效、以及外部参与方能访问什么。应先通过目标架构和控制项确认这些语义，再进入实现与生产迁移。
