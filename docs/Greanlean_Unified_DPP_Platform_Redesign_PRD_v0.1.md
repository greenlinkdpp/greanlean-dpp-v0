# Greanlean 统一 DPP 平台与官网重构需求

> 文件类型：产品需求文档（PRD）
> 目标版本：Greanlean v0.5.0 — Unified DPP Platform
> 文档版本：v0.1
> 日期：2026-07-24
> 状态：待确认，当前仅生成需求文件，不执行开发
> 前置版本：Greanlean v0.4.0 — Battery Passport Demo Expansion

---

## 0. 本次需求结论

本版本不再把工业储能电池做成独立的特殊页面，而是建立一套覆盖所有产品的统一 DPP 展示框架。

核心决策如下：

1. 官网从“电池护照优先首页”调整为“全行业 DPP 平台首页”；
2. 电池护照保留为官网中的独立重点板块，但不占据整个平台的唯一主叙事；
3. 首页保留四个重点产品护照案例：
   - LMT 电池；
   - 工业储能电池；
   - 纺织品；
   - 消费电子；
4. 四个案例卡片和四个公开 DPP 页面使用同一套版式、模块规则和视觉系统；
5. 工业储能电池不再维护独立页面组件和独立静态数据源；
6. 所有产品数据均从统一产品、行业字段、证据文件和生命周期数据结构读取；
7. 前台页面不再显示“合成演示数据”“演示产品”等字样；
8. 后台仍必须记录数据来源、验证状态、证据文件和责任主体，防止把未验证数据误当成第三方结论；
9. 扫码本身不能证明用户身份；受限数据必须通过登录、组织身份、角色和服务器权限投影控制；
10. 电池页面新增“运行状态与健康数据”模块，并预留 BMS、EMS、设备网关和维保系统接口。

# 一、现状分析

## 1.1 官网现状

当前首页已经强化电池护照，但整体叙事偏向电池，不能完整表达 Greanlean 是一个面向多行业的 DPP 平台。

目前存在以下问题：

- 全局 DPP 能力与电池专属能力的层级不清晰；
- 法规、产品分类、实施流程、系统能力和案例之间缺少明确的信息路径；
- 四个重点案例虽然存在，但案例卡片的信息密度、标签和视觉重点没有完全统一；
- 电池法规时间节点与其他 ESPR 产品组时间节点缺少统一展示；
- 首页的能力说明没有充分区分“当前已实现”“系统已预留”“法规尚待授权法案确认”。

## 1.2 DPP 展示页现状

当前至少存在两套展示逻辑：

1. 通用产品使用 `PublicDppClient`；
2. 工业储能电池使用独立的 `BatteryDemoPassport`。

由此产生：

- 页头、导航、信息分组和数据状态样式不一致；
- 工业电池页面的能力无法自然复用到纺织品和消费电子；
- 通用页面后续优化时，工业电池页面不会自动同步；
- 工业电池维护了静态回退数据，与数据库产品记录形成双重权威数据源风险；
- 同一个平台对消费者呈现出两套不同的产品体验。

## 1.3 数据现状

工业储能电池当前同时存在：

- TypeScript 静态产品模型；
- JSON 样例数据；
- Supabase Seed；
- 产品中心同步逻辑；
- 通用产品表和电池专属表。

目标状态必须收敛为：

```text
数据库产品记录
→ 通用 DPP 基础模块
→ 行业模板和行业字段值
→ 电池专属模型、批次、单体和运行指标
→ 证据文件、版本和权限投影
→ 统一 DPP 页面
```

静态 JSON 或 Seed 仅用于初始化数据库，不得成为线上展示页面的长期第二数据源。

## 1.4 权限现状

当前权限能力属于“部分完成”：

- 通用 DPP 页面可以通过 `view=consumer/professional/audit` 切换展示模式；
- 仅依靠 URL 查询参数不能确认访问者身份，也不能构成安全权限；
- 电池公开 API 已经具备登录令牌和服务器权限投影基础；
- 电池权限可以读取用户 `app_metadata.dpp_access_level`；
- 工业电池独立静态页面没有完整接入上述服务器权限投影；
- 当前尚未形成组织认证、角色审批、访问申请和审计记录的完整闭环。

结论：

> 当前可以演示不同视图，但不能把所有现有视图都称为已经完成安全权限控制。

## 1.5 动态数据现状

当前系统已经具备以下基础：

- 电池运行指标目录；
- SOH、SOC、温度、内阻、循环次数等字段；
- BMS、设备网关、人工记录、维保记录等数据来源类型；
- 运行指标只追加、不覆盖的历史结构；
- 后台人工追加运行数据的界面；
- 部分电池页面的受限运行数据表格。

当前不足：

- 统一 DPP 页面没有固定的“电池运行状态与健康数据”板块；
- 最新快照和历史趋势缺少一致的信息架构；
- 没有稳定的外部设备接入 API 契约；
- 没有设备身份、幂等键、质量状态和数据新鲜度提示；
- 没有明确区分实时遥测、定时快照和生命周期事件。

# 二、参考平台与设计原则

## 2.1 参考对象

本次官网和产品信息架构可参考以下平台，但不得复制其品牌、图片、文案或页面：

### Circularise

参考点：

- 以统一 DPP 平台为主叙事；
- 按行业展示适配能力；
- 强调模板、批量操作、API 和系统集成；
- DPP、供应链和可验证数据统一表达。

参考链接：

https://www.circularise.com/digital-product-passports

### Minespider

参考点：

- DPP 与电池护照属于同一平台；
- 电池护照作为独立重点解决方案；
- 强调材料、供应链、碳足迹、生命周期和权限；
- 面向消费者、供应链伙伴和监管主体提供不同数据。

参考链接：

https://www.minespider.com/

### Circulor

参考点：

- 不只展示字段，强调字段背后的证据和供应链可信度；
- 将 DPP、尽职调查、验证和风险管理放在同一产品叙事下；
- 突出从声明到证据的可信链路。

参考链接：

https://circulor.com/

## 2.2 Greanlean 设计原则

1. 全局平台优先，电池能力重点突出；
2. 一个 DPP 页面框架，多个行业配置；
3. 一个产品只对应一个权威数据源；
4. 公众页面以产品信息为中心，不直接展示法规字段目录；
5. 专业和监管页面可以展示字段编码、法规依据、数据来源和证据状态；
6. 页面不通过颜色暗示“全部合规”；
7. 用户看到的是产品信息，不是数据库字段清单；
8. 统一结构中允许行业模块不同，但页头、导航、状态、表格和文档组件必须一致；
9. 中英文保持同一信息层级，不得出现一方缺字段或中英混排说明；
10. 产品数据更新后，公开页面、专业页面、二维码和导出文件使用同一发布版本。

# 三、版本目标与非目标

## 3.1 版本目标

形成以下统一链路：

```text
官网了解 DPP
→ 查看行业与法规进度
→ 重点了解电池护照
→ 查看四个产品护照案例
→ 扫码或点击进入统一 DPP 页面
→ 公众直接查看公开信息
→ 专业用户登录后查看获授权信息
→ 电池用户查看最新运行快照和历史趋势
→ 后台通过统一数据模型维护和发布
```

## 3.2 本版本包括

- 官网整体重新布局；
- 中英文切换；
- 全局 DPP 平台叙事；
- 电池护照独立重点板块；
- 法规进度和预计时间线；
- 四个统一版式案例；
- 全产品统一 DPP 页面框架；
- 删除工业电池专属展示页面逻辑；
- 数据来源收敛到数据库；
- 公开、专业、监管和内部权限设计；
- 电池动态数据展示板块；
- BMS、EMS、网关和维保系统 API 契约；
- 当前四个案例数据的标准化；
- 桌面端和移动端适配；
- 测试、迁移、回滚和发布文档。

## 3.3 本版本不包括

- 正式接入任意一家真实 BMS 厂商；
- 秒级实时监控平台；
- 替代 EMS 或 SCADA；
- 正式 EU Registry 生产凭据管理；
- 自动生成真实合规结论；
- 自动签发检测报告或证书；
- 自动完成第三方核查；
- 与需求无关的后台架构重写；
- 为每个行业单独开发一套页面。

## 4.2 首页模块顺序

### 模块 1：全局 Hero

主标题应表达 Greanlean 是全行业数字产品护照平台。

中文建议：

```text
面向欧盟市场的数字产品护照平台
```

英文建议：

```text
Digital Product Passports for the EU Market
```

副标题覆盖：

- 行业模板；
- 数据采集；
- GS1 标识与二维码；
- 权限控制；
- 证据和版本；
- Registry 准备；
- 生命周期持续更新。

主要操作：

- 查看产品护照案例；
- 了解平台流程。

Hero 不单独以电池为唯一主题。

### 模块 2：法规与实施进度

以横向时间线展示已经明确和仍待确认的节点。

页面必须区分：

- 法规确定日期；
- 欧盟工作计划中的预计授权法案采纳时间；
- 授权法案正式适用日期；
- 仍待实施文件确认的日期。

建议时间线：

| 时间 | 产品/事项 | 页面表述 |
|---|---|---|
| 2024-07 | ESPR 生效 | 建立跨产品 DPP 总体框架 |
| 2026-07 | DPP Registry 实施安排 | Registry 保存注册和唯一标识等数据；具体行业语义仍由适用规则决定 |
| 2027-02-18 | 电池护照 | LMT、电动汽车电池、额定能量大于 2 kWh 的工业电池开始适用电池护照要求 |
| 2027（预计采纳） | 纺织品/服装 ESPR 措施 | 这是预计授权法案采纳时间，不等同于最终强制实施日期 |
| 2028（预计采纳） | 家具 ESPR 措施 | 最终字段和适用日期等待授权法案 |
| 2027 / 2029（横向措施预计采纳） | 消费电子相关维修性、再生含量和可回收性 | 不得表述为全部消费电子在该日期统一强制使用 DPP |

法规来源：

- Regulation (EU) 2024/1781；
- Regulation (EU) 2023/1542；
- Commission Implementing Regulation (EU) 2026/1778；
- ESPR and Energy Labelling Working Plan 2025–2030, COM(2025) 187 final。

时间线底部必须显示：

```text
预计采纳时间不等于最终适用日期。实际产品范围、字段、粒度和实施日期以正式授权法案及后续实施文件为准。
```

### 模块 3：平台工作流程

统一为六步：

1. 判断产品和法规适用性；
2. 选择行业、产品类别和数据粒度；
3. 采集企业、供应商、检测和运行数据；
4. 建立标识、字段、证据和权限关系；
5. 发布二维码、网页和机器可读数据；
6. 持续更新生命周期、证据和注册状态。

### 模块 4：行业方案

当前官网重点展示：

- 电池；
- 纺织品；
- 家具；
- 建材；
- 消费电子。

每个行业显示：

- 适用产品分类；
- 核心数据模块；
- 当前平台支持程度；
- 查看对应案例或方案。

板块应包含：

- 制造商和经济运营者；
- 材料和关注物质；
- 碳足迹；
- 再生材料；
- 性能和耐久性；
- 拆卸、维修和安全；
- 生命周期事件；
- 运行状态与健康数据；
- 合规和证据文件；
- Registry 注册准备。

#### 动态数据说明

页面明确说明：

```text
电池护照不是秒级实时监控系统。Greanlean 保存最新状态快照、历史趋势和重要生命周期事件，并可通过 BMS、EMS、设备网关或维保系统持续更新。
```

#### 时间节点

至少展示：

# 五、统一 DPP 展示框架

## 5.1 页面组件原则

所有产品使用一个统一页面框架，例如：

```text
UnifiedDppPage
├── DppHeader
├── ProductHero
├── PassportIdentity
├── AudienceProjection
├── SectionNavigation
├── CommonProductModules
├── SectorSpecificModules
├── EvidenceAndDocuments
├── LifecycleAndUpdates
└── FooterAndResolver
```

禁止继续维护：

```text
工业储能电池独立页面
纺织品独立页面
消费电子独立页面
```

允许通过行业配置决定模块是否显示，但不得复制整套页面。

## 5.2 统一页面顶部

所有产品顶部保持同一布局：

- 产品图片；
- 产品名称；
- 行业和产品类别；
- 品牌或制造商；
- DPP ID；
- UPI；
- GTIN/SGTIN（适用时）；
- 型号、批次、单体粒度；
- 二维码；
- 4 个行业关键指标；
- 数据更新时间；
- 生命周期状态。

公开页面不显示：

- 内部数据版本；
- 后台字段目录版本；
- 已验证证书数量；
- 面向开发者的 Schema 信息；
- 受限数据入口切换按钮。

## 5.3 统一模块顺序

所有产品使用以下一级模块顺序：

1. 产品身份与制造信息；
2. 材料与组成；
3. 环境与可持续性；
4. 性能、耐久性与安全；
5. 供应链与生产追溯；
6. 合规声明与证据文件；
7. 维修、循环利用和生命周期结束；
8. 生命周期事件与更新。

行业专属模块插入规则：

- 电池：运行状态与健康数据；
- 纺织：纤维成分、护理、微塑料和生产工序；
- 消费电子：零部件、能效、维修、WEEE 和内置电池信息；
- 家具：木材来源、耐久性、维修和拆解；
- 建材：性能声明、材料组成、施工、维护和回收。

## 5.4 四个案例版式对齐

四个案例必须满足：

- 相同首屏高度规则；
- 相同图片比例；
- 相同标题层级；
- 相同关键指标数量；
- 相同一级导航结构；
- 相同折叠交互；
- 相同文件组件；
- 相同状态标签；
- 相同移动端断点；
- 相同中英文切换位置。

行业字段数量可以不同，但视觉结构不能重新设计。

## 5.5 数据来源

页面只能从以下发布数据读取：

- `products`；
- 通用产品模块表；
- 行业字段值；
- 电池型号、批次和单体表；
- 电池运行指标；
- 生命周期事件；
- 证据和文件；
- 已发布版本快照。

静态文件只允许：

- 开发测试 fixture；
- 数据库初始化 Seed；
- Schema 示例；
- 自动化测试样例。

线上页面不得在数据库缺失时偷偷切换到另一套完整静态产品。

# 七、扫码身份与访问权限

## 7.1 基本结论

二维码只能提供产品或单体的稳定访问地址，不能自动知道扫码者是谁。

以下做法不能视为安全权限：

- `?view=professional`；
- `?view=audit`；
- 前端隐藏模块；
- 不同颜色的二维码；
- 把角色写在 URL 中；
- 仅依靠页面按钮切换。

## 7.2 目标访问流程

### 公众访问

```text
扫码
→ 打开稳定 UPI
→ 直接返回 PUBLIC 数据
```

### 专业或合法利益主体

```text
扫码
→ 打开公开页面
→ 选择登录或访问受限信息
→ Supabase Auth / 企业 SSO 验证
→ 读取用户所属组织和获批角色
→ 服务器计算访问等级
→ 返回对应字段投影
→ 记录访问审计
```

### 监管机构

```text
扫码或访问监管入口
→ 强身份认证
→ 验证监管角色和适用范围
→ 服务器返回 AUTHORITY_ONLY 数据
→ 记录访问目的、时间和数据范围
```

## 7.3 权限角色

建议角色：

| 角色 | 访问等级 | 典型数据 |
|---|---|---|
| 公众/消费者 | PUBLIC | 产品、材料概览、基础环境和回收信息 |
| 采购商/合作伙伴 | LEGITIMATE_INTEREST | 详细组成、供应链、维修、运行快照 |
| 维修商/再利用/回收商 | LEGITIMATE_INTEREST | 拆解、安全、部件、剩余性能 |
| 监管机构/公告机构 | AUTHORITY_ONLY | 完整证据、详细验证和受限记录 |
| 企业内部管理员 | INTERNAL | 草稿、审批、接口、审计和全部原始数据 |

## 7.4 技术要求

权限必须由服务器执行：

- 登录令牌校验；
- 用户与组织关系；
- 组织角色；
- 产品或产品组授权范围；
- 字段访问等级；
- 数据库 RLS；
- API 权限投影；
- 访问日志；
- 权限失效和撤销。

URL 中的 `view` 只允许后台管理员预览，不得决定公开访问权限。

## 7.5 二维码策略

优先使用一个二维码：

```text
一个物理二维码
→ 一个稳定 UPI
→ 未登录返回公众信息
→ 登录后由服务器返回获授权信息
```

不建议为每个角色印刷不同二维码，因为二维码可能被转发、拍照或复制。

如客户需要邀请链接，只能用于启动登录和授权申请，不能把链接本身作为永久权限凭证。

## 8.1 页面定位

```text
运行状态与健康数据
Operating Status & Battery Health
```

- 容量衰减；
- 当前生命周期状态；
- 最近测量时间；
- 来源设备；

### 历史趋势

至少支持：

- SOC；
- SOH；
- 温度；
- 内阻；
- 容量；
- 累计循环；
- 能量吞吐量。

时间范围：

- 24 小时；
- 7 天；
- 30 天；

### 事件记录

- 维修；
- 故障；
- 安全事件；
- BMS 更换；
- 再利用；
- 改变用途；
- 退役；
- 回收。

## 8.3 初始产品数据

在尚未接入真实设备前，可以写入初始化数据，但前台不使用“假数据”“演示数据”字样。

后台必须将其记录为：

```text
data_source = INITIAL_DATASET
verification_status = UNVERIFIED
source_device = INITIAL-IMPORT
```

初始数据不得伪装成设备实时上报。

## 8.4 更新模式

电池护照不做秒级监控，建议支持：

| 模式 | 用途 |
|---|---|
| DAILY_SNAPSHOT | 每日 BMS 状态快照 |
| EVENT_DRIVEN | 故障、维修、安全和状态变化 |
| SERVICE_SNAPSHOT | 无法自动联网时的维保记录 |
| MANUAL_VERIFIED_IMPORT | 经核验的批量导入 |

页面必须显示“最后更新时间”和“数据是否过期”。

## 8.5 接口设计

建议接口：

```text
POST /api/integrations/battery/items/{itemId}/metrics
POST /api/integrations/battery/items/{itemId}/events
GET  /api/battery-dpp/items/{itemId}/metrics/latest
GET  /api/battery-dpp/items/{itemId}/metrics/history
```

单条指标至少包含：

```json
{
  "itemId": "string",
  "metricCode": "SOH",
  "value": 98.7,
  "unit": "%",
  "measuredAt": "2026-07-24T10:30:00Z",
  "receivedAt": "2026-07-24T10:30:05Z",
  "sourceSystem": "BMS",
  "sourceDevice": "BMS-ESS-GW-001",
  "qualityStatus": "VALID",
  "verificationStatus": "DEVICE_REPORTED",
  "idempotencyKey": "string",
  "signature": "optional"
}
```

## 8.6 接口安全

必须支持：

- API Key 或 OAuth 2.0 Client Credentials；
- 每个客户和设备独立凭据；
- 凭据轮换；
- 请求签名或 mTLS 预留；
- 时间戳校验；
- 幂等键；
- 重放攻击防护；
- 指标范围校验；
- 单位校验；
- 设备与电池绑定；
- 限流；
- 接入日志；
- 错误重试；
- 不可覆盖历史记录。

## 8.7 数据存储

动态数据继续使用只追加模式：

```text
battery_operating_metric
```

不得通过更新旧记录来修改历史。

如需修正：

- 追加纠正记录；
- 引用原记录 ID；
- 保留原因、操作人和时间。

# 十三、风险和处理

## 风险 1：移除“演示”字样造成真实性误解

处理：

- 前台使用正常产品表达；
- 后台保留来源和验证状态；
- 不展示虚构第三方结论；
- 专业页面显示“企业声明、文件支持、第三方验证”等中性状态。

## 风险 2：统一页面导致行业特色丢失

处理：

- 统一页面框架；
- 允许行业专属模块；
- 行业差异通过配置和数据表现，不通过复制页面表现。

## 风险 3：二维码权限被误解

处理：

- 一个二维码只解析产品身份；
- 登录身份决定权限；
- 查询参数不能提权；
- 服务器和数据库共同执行权限。

## 风险 4：动态数据被误解为实时监控

处理：

- 使用最新快照和历史趋势；
- 显示采集时间和数据新鲜度；
- 不承诺秒级实时性；
- 监控告警仍由 BMS、EMS 或 SCADA 承担。

## 风险 5：法规时间线产生错误承诺

处理：

- 区分法规确定日期、预计采纳和正式适用；
- 每个时间节点显示依据；
- 法规配置支持后续更新；
- 不把 ESPR 工作计划年份直接当作产品强制实施日。
