# Battery Passport Demo Current Impact Analysis

Date: 2026-07-24
Target release: v0.4.0
Implementation branch: `feature/battery-passport-demo`

## 1. Current State

### Technology and deployment

- Frontend and server routes: Next.js 14 App Router, React 18, TypeScript and Tailwind CSS.
- Data and authentication: Supabase PostgreSQL, Supabase Auth and row-level security.
- Public deployment: Vercel at `https://www.greanlean.com`.
- QR codes: generated as PNG by `/api/qr` using the `qrcode` package.
- Public exports: generated by `/api/dpp-export`.
- Local and CI checks: repository lint, TypeScript, Node unit/integration tests, migration tests, Next.js build and smoke tests.

### Existing public experience

- The homepage is a general DPP service page.
- The current four featured cases are textile, consumer electronics, construction material and furniture.
- The public DPP route is `/p/[slug]`; existing URLs support `lang=zh|en` and consumer, professional and audit views.
- Existing LMT battery records use the same public DPP route and project a small subset of the battery field catalogue into the legacy public layout.
- Public consumers do not see restricted operating metrics. Professional and audit views are selected by the application and protected server-side when they request battery regulatory data.

### Existing battery foundation

- Six legal battery categories are represented: EV, LMT, industrial, portable, SLI and other.
- Industrial batteries are classified into stationary above 2 kWh, non-stationary above 2 kWh and without-BMS variants.
- The BatteryPass-Ready v1.3 reference catalogue contains 100 versioned fields in seven source groups:
  - product and battery identity: 20
  - conformity documents: 7
  - materials and composition: 5
  - carbon footprint and sustainability: 8
  - due diligence: 3
  - performance and durability: 42
  - circularity and safety: 15
- Twenty-two catalogue fields are dynamic. Append-only history is already supported by `battery_operating_metric`.
- Existing normalized tables cover model, batch, item, field values, material composition, sustainability, performance, documents, disassembly, lifecycle events and operating metrics.
- Existing field definitions retain code, bilingual labels, type, unit, granularity, access level, requirement status, source, evidence expectation and regulatory reference.

### Existing demo data

- The four legacy demo products and routes remain useful and must be preserved.
- The LMT battery has a database seed and public product image.
- No GreenVault industrial battery product, public fallback, database seed or dedicated industrial-battery presentation currently exists.
- The supplied `docs/industrial-battery-demo.seed.json` provides the canonical synthetic values for the new demo.

## 3. Reuse Strategy

- Keep `/p/[slug]` as the canonical public passport route and add stable aliases for the PRD routes.
- Reuse the existing public header, QR endpoint, language query, audience views and general DPP sections.
- Add one battery demo presentation model shared by LMT and industrial profiles instead of duplicating public-page code.
- Keep the 100-field catalogue as the regulatory mapping source. The public UI will present product information by user task, not dump raw regulatory field names.
- Use the existing normalized battery tables for database storage. Do not add battery-specific columns to `products`.
- Use `battery_operating_metric` for every synthetic BMS measurement so history remains append-only.
- Keep the supplied JSON file as the human-readable canonical fixture and derive static fallback and SQL seed values from the same identifiers.

## 5. Database and Migration Decision

No schema migration is required. Migrations `0009` and `0010` already provide every object required by the PRD.

An idempotent seed is required to:

- upsert the generic product record;
- create or update the stationary industrial battery model profile;
- create the batch and item;
- populate static field values with source and verification metadata;
- add material, sustainability, performance, document, disassembly and lifecycle records;
- append synthetic operating metric history only when the timestamped measurement is absent.

The seed must fail clearly when prerequisite migrations are not installed and must not modify unrelated products.

## 6. Risks and Controls

- **Regulatory overstatement:** all new values are marked `SYNTHETIC_DEMO`; documents are placeholders; Registry and third-party verification remain unavailable.
- **Two sources diverging:** stable identifiers and tests will compare the fallback fixture, route response and SQL seed contract.
- **Public data leakage:** public rendering consumes only public fields; restricted projections continue to use server authorization.
- **Legacy regression:** old demo records, URLs and database rows are not deleted. Only homepage featuring changes.
- **Database not yet seeded:** the public static fallback prevents 404; product-center visibility requires running the provided idempotent seed or authenticated sync.
- **Fake live telemetry:** operating metrics display a fixed source, timestamp and synthetic status, never a live indicator.
- **External image ownership:** use a locally generated, unbranded industrial battery image stored in the repository.

## 8. Rollback

- Revert the v0.4.0 implementation commit to restore the previous homepage and public rendering.
- The SQL seed uses stable demo identifiers. Its rollback deletes only the GreenVault demo item, batch, model profile, related battery rows and generic product record.
- Existing LMT and legacy demo data are outside the rollback scope and remain untouched.
- Vercel can be rolled back to the previous production deployment after the code revert.
