# 迁移、发布与回滚要求

## 1. 迁移原则

- 先盘点再迁移；
- 先兼容新增，再切换读取，再清理旧结构；
- 避免一次性重写全部历史DPP数据；
- 迁移可重放、可校验、可暂停；
- 生产迁移前在脱敏副本或结构等价环境演练；
- 迁移脚本记录批次、行数、错误和校验哈希。

## 2. 旧数据分类

Codex审核后将现有记录至少分为：

1. 可直接映射到Organisation-Model-Item；
2. 只有型号、无单体序列号的演示/型号展示；
3. 存在序列号但粒度表达冲突；
4. 标识/UPI不满足HTTPS或唯一性；
5. 已发布但无不可变快照；
6. 证据文件存在但未关联字段/范围；
7. 数据逻辑冲突或单位不明确；
8. Registry状态需要降级或重新标记。

不得为缺失事实自动生成真实序列号、正式URI或第三方验证结论。

## 3. 推荐迁移阶段

### Stage 0 备份与观测

- 数据库快照；
- 文件清单和哈希；
- 公共URL清单；
- 当前记录数量和关键约束报告。

### Stage 1 兼容Schema

- 新增表/字段和nullable关系；
- 不删除旧字段；
- 新代码可读旧数据；
- Feature Flag关闭新发布。

### Stage 2 回填

- 建Organisation/Model/Item映射；
- 标记演示或待确认；
- 生成候选UPI但不覆盖旧URL；
- 创建历史快照时标明`MIGRATED_LEGACY`和来源；
- 输出冲突报告，不静默选择。

### Stage 3 双读/双写或适配

- 新创建使用新模型；
- 旧页面通过适配器读取；
- 对比新旧输出；
- 逐步切换公共解析。

### Stage 4 切换

- 开启新发布；
- 监控UPI、错误、PDF/JSON和权限；
- 保留旧路由重定向；
- 可快速关闭Feature Flag。

### Stage 5 清理

只有在验证周期结束且有备份/回滚后，才处理废弃结构。清理不是P0必要条件。

## 4. 发布检查

- 环境变量和秘密；
- 数据库迁移状态；
- 对象存储权限；
- 后台任务和队列；
- 公共域名、HTTPS和重定向；
- 缓存失效；
- Feature Flags；
- 监控和告警；
- 支持与回滚联系人；
- 手工烟雾测试。

## 5. 回滚

回滚方案至少说明：

- 应用版本回滚；
- 数据库向前修复或反向迁移；
- 新旧路由切换；
- Feature Flag关闭；
- 后台任务停止与重放；
- 文件和发布快照恢复；
- 迁移期间写入数据如何处理。

禁止将“恢复数据库备份”作为唯一回滚方法而不说明恢复点后的数据损失。
