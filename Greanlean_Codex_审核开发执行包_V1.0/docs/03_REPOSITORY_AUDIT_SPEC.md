# 现有代码库审核规格

## 1. 审核目标

审核必须回答四个问题：

1. 现在系统真实能做什么；
2. 与M01-M18相比缺什么、错什么、哪些只是界面假象；
3. 哪些部分可以增量复用，哪些需要迁移或重构；
4. P0怎样以最小风险上线。

## 2. 审核范围

### 2.1 代码与架构

- 前端、后端、共享包、脚本、基础设施；
- 路由、状态管理、API客户端、服务层、领域层、数据访问层；
- 数据库、迁移、种子、缓存、队列、对象存储；
- 多语言、PDF、二维码、文件上传、JSON输出；
- Registry、BMS、ERP/MES预留代码；
- 错误处理、日志、审计、监控。

### 2.2 安全

- 认证方式和会话生命周期；
- 租户隔离是在查询层、数据库层还是仅前端；
- RBAC/ABAC；
- 对象级越权；
- 文件直链和导出；
- 密钥及环境变量；
- 输入校验、上传类型、恶意文件、路径遍历；
- 日志中的隐私和秘密。

### 2.3 数据

- 当前实体、字段、约束、索引、外键和软删除；
- 型号、批次、单体的真实关系；
- 已发布版本是否可被修改；
- 公开页面、PDF、JSON是否读取同一快照；
- 当前标识唯一性和URL稳定性；
- 证据与数据是否有可追溯关联；
- 数据迁移和生产兼容风险。

### 2.4 工程质量

- 构建、测试、Lint、类型检查；
- CI/CD和部署；
- 测试隔离、Fixtures和Mock；
- 依赖健康；
- 代码重复、模块耦合和技术债；
- 可观测性和恢复能力。

## 3. 审核证据要求

每个结论必须引用至少一种证据：

- 文件路径及代码符号；
- 数据库迁移或Schema；
- 实际命令和输出摘要；
- 测试名称及结果；
- 路由/API；
- 页面或公共URL；
- 配置或部署定义。

不允许只写“看起来已实现”。

## 4. 风险等级

- `CRITICAL`：数据泄露、跨租户访问、数据丢失、公开凭据、Registry假成功；
- `HIGH`：发布版本可变、UPI冲突、无证据发布、迁移不可回滚、权限只在前端；
- `MEDIUM`：错误处理不完整、测试不足、字段不一致、性能或运维隐患；
- `LOW`：样式、命名、非关键重复和文档缺失。

## 6. 审核期间禁止事项

- 不自动格式化全仓库；
- 不升级依赖；
- 不生成迁移；
- 不修改生产配置；
- 不向外部API发送真实请求；
- 不重写现有模块；
- 不提交或推送代码。
